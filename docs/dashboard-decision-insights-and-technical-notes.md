# 臺北不動產與城市脈絡儀表板：決策洞察與技術設計說明

## 一、專案定位

這是一個以臺北市政府開放資料為基礎的探索型儀表板。它把實價登錄、住宅與商辦租售指標、都市計畫與土地資料、建照／使用執照、人口、所得、消費者物價、用電與若干公共資產資料整理成同一個可篩選、可比較的介面。

它的目的不是替使用者估價、預測價格或給出投資結論，而是縮短「取得資料、理解欄位、清理格式、交叉檢視脈絡」之間的距離。使用者應以它提出更好的問題，再回到主管機關公告、契約或專業意見完成查證。

## 二、可以支援的決策問題

### 1. 區域研究與初步盤點

在討論某行政區的居住、開發或公共設施議題時，可同時查看交易紀錄摘要、人口結構、所得、土地使用管制、建築執照及價格／租金指標。這有助於辨識資料之間是否存在值得追問的現象，例如：人口成長與建照量是否同步、交易單價變化是否與全市指數方向相近、土地使用管制是否限制了某些開發假設。

適合情境：

- 政策研究或社區議題的前期資料盤點。
- 不動產服務、都市規劃或研究團隊的區域背景整理。
- 內容團隊製作圖表、報告或公開說明前的資料核對。

不適合情境：

- 單一門牌、單一地號或單一建物的即時價格判定。
- 直接根據圖表做出買賣、授信、稅務、法律或投資決策。

### 2. 趨勢與脈絡比較

儀表板將月／季住宅價格指數、住宅租金指數、商辦租金指數、CPI、所得與用電等資料保留為獨立資料集，並以時間序列或區域摘要呈現。這種設計的價值在於比較「是否同向」、「何時開始變化」、「哪一層級的資料可支持觀察」，而不是把相關性誤當成因果。

例如，當住宅價格指數上升時，可進一步查看租金指標、所得或 CPI 是否也在變動；若沒有同步，也能避免過度簡化地用單一指標解釋市場。

### 3. 公共資料的行政紀錄檢視

專案亦涵蓋公告徵收清冊、市地重劃抵費地歷史標售、申報地價、經紀業名冊、估價師名冊、消費爭議與裁罰等資料。這些模組都將資料定位為「歷史或行政來源紀錄」，避免延伸成目前權利、營業資格、責任、可購買性或風險評分。

適合用於：

- 公共工程、地政資料與市場服務資料的歷史整理。
- 對資料欄位、涵蓋期間與來源限制的可視化說明。
- 需要保留資料原文、下載篩選結果、回溯來源的研究工作。

## 三、資料解讀原則

1. **來源欄位優先於衍生欄位。** 原始單位、日期、文字說明和識別碼會保留；坪數、每坪金額、比率等衍生值都有明確標示。
2. **缺失不是零。** 空白、破折號、無法解析的值維持缺失，避免把「沒有資料」轉成零而影響統計。
3. **資料集不被強制合併。** 經紀業名冊、裁罰與消費爭議分開呈現；同名不代表同一法律主體，也不應自動產生風險標籤。
4. **沒有官方座標就不畫點。** 地號、段小段與地址文字不會自動地理編碼，也不會產生看似精確但無依據的地圖標記。
5. **行政數值不等於市場價格。** 公告／申報地價、歷史得標價格、租金指標、稅率與公共資產紀錄各有行政意義，不能直接替代成交價格、估價或投資報酬。

## 四、資料處理架構

資料流程可概括為：

```text
官方下載檔／人工放置的原始檔
        ↓
Node.js 擷取與格式辨識（UTF-8-SIG、Big5／CP950）
        ↓
轉換腳本：保留原文、解析日期與數字、建立資料品質訊號
        ↓
public/data 下的靜態 JSON 與摘要檔
        ↓
React 儀表板：依頁籤與需求載入、篩選、繪圖與 CSV 匯出
```

前端不在瀏覽器直接呼叫臺北開放資料 API。這讓展示結果較可重現、降低使用者開啟頁面時受到上游連線或跨網域限制的影響，也能先完成資料清理後再提供互動查詢。

## 五、實作過程中需要處理的問題與作法

### 1. 大型來源檔造成記憶體與載入壓力

**問題：** 建築使用執照 XML 等來源檔案很大。若一次讀入記憶體、完整轉為單一 JSON，再由瀏覽器全量下載，會同時增加轉換程序與使用者端的負擔。

**採用作法：**

- 在建置階段以 Node.js 串流解析大型 XML，而非先完整載入。
- 產生年度摘要與分年 JSON chunk。
- 前端預設只讀摘要；需要列表或細節時才載入相關年份區塊與明細。

**為何適合：** 儀表板的初始畫面通常只需要總量、趨勢與分布，不需要所有原始明細。將「摘要」和「明細」分層可直接減少首屏資料量。

**取捨：** 需要維護 manifest、分檔命名與按需載入邏輯；若使用者經常跨所有年份進行全文檢索，分塊會增加請求次數。

**可替代方案：**

- 若資料與查詢需求持續成長，可改以後端資料庫與 API 提供分頁、索引和聚合。
- 若需離線分析，可使用 Parquet／DuckDB-WASM 等欄式格式；代價是瀏覽器相容性、套件體積與操作複雜度會提高。
- 若資料量中等、互動要求極低，單一壓縮 JSON 的維護成本最低，但不適合大型明細。

### 2. 前端初始載入與 JavaScript chunk 警告

**問題：** 圖表元件與 React DOM 會讓單一 bundle 偏大，產生建置警告並延長首次下載與解析時間。

**採用作法：** 在 Vite 的 `manualChunks` 將 React、React DOM 與 Recharts／D3 相關依賴拆成穩定的 vendor chunk。

**為何適合：** 這些函式庫在多個頁籤重複使用，拆出後能讓瀏覽器快取共用依賴，也讓主程式 chunk 較小。它不改變產品功能或資料內容。

**取捨：** chunk 變多代表初次進入涉及圖表的頁面時可能多一個請求；在網路極差且使用者只會看單一頁面時，過度拆分未必更快。

**可替代方案：**

- 對少用的大型模組使用 `React.lazy` 進行頁籤級動態載入。
- 以較輕量的圖表元件或原生 SVG 取代部分 Recharts 圖表。
- 若部署環境有 HTTP/2/3、長效快取和使用者回訪，維持 vendor chunk 通常較有利；若是單次內網展示，則可依量測結果調整拆分策略。

### 3. 編碼、日期、單位與來源欄位不一致

**問題：** 開放資料常見 UTF-8-SIG、Big5／CP950 並存；ROC 年、Gregorian 年、日期字串、千元、平方公尺、坪、百分比及欄名標點也各不相同。

**採用作法：**

- CSV 讀取先嘗試 UTF-8，必要時回退 Big5／CP950。
- 統一的日期與數值解析工具以保守規則處理，無法確認的資料保留原文並標為缺失。
- 以別名比對欄位，容許合理的空白與標點變化。
- ROC 年只在格式足以確認時轉為 Gregorian；原始值同時保留。

**為何適合：** 這比「假設每份 CSV 都是同一編碼與 schema」可靠，且能把不確定性留在資料品質結果中，而不是悄悄製造錯誤數字。

**取捨：** 規則越保守，可解析筆數可能越少；但對公共資料儀表板而言，將未知呈現為未知通常比錯誤補值更可接受。

### 4. 識別碼與地籍編碼不能當一般數字

**問題：** 地號、登錄號碼、機關代碼、憑證字號與持分欄位可能含前導零、連字號或文字後綴。若轉成數字，會破壞辨識與比對。

**採用作法：** 原始識別碼以字串保存；只有在官方規則明確時才建立額外的顯示欄位。例如申報地價的八碼地號會保留 raw code，並以文件化 parser 轉成 `1` 或 `1-1` 形式供閱讀。

**取捨：** 字串欄位不能直接做數值排序；但保留資料語意比方便排序更重要。需要排序時應另建安全的排序鍵，而非覆蓋原值。

### 5. 對敏感或易被誤解資料維持安全邊界

**問題：** 裁罰、消費爭議、名冊、徵收、估價師與地籍資料很容易被錯誤延伸為「現況不合規」、「目前可買」、「有風險」或「市場價格」。

**採用作法：**

- 各模組明示資料期間、來源、限制與不適用事項。
- 裁罰、名冊與消費爭議不做同名自動合併與評分。
- 行政地價、歷史標售、公告徵收只顯示歷史／行政意義。
- 沒有官方座標與幾何資料時，不畫地圖點位與界址。

**取捨：** 少了吸睛的排名、風險分數與地圖互動；換來的是更可說明、較不誤導的資訊產品邊界。

## 六、可展示的使用流程

1. 先從市場總覽或價格／租金指數建立時間脈絡。
2. 以行政區比較人口、所得、建照、土地使用與交易摘要，找出需要進一步查證的差異。
3. 進入專題模組（如公共資產、地籍、服務業名冊或消費爭議）後，使用篩選器縮小資料範圍。
4. 下載當前篩選結果，保留分析條件並交由試算表、統計工具或正式研究流程續作。
5. 對關鍵結論回到官方公告、地政事務所、招標文件或主管機關資料查驗。

## 七、後續可擴充方向

- 建立資料來源更新狀態頁，顯示最後下載時間、涵蓋期間、解析成功率與欄位異動。
- 將共通的篩選、表格、CSV 匯出與資料品質元件抽成可重用元件，降低新增模組的重複程式。
- 若需要多人使用與大量跨資料查詢，可導入後端聚合 API、資料庫索引與權限／審計機制。
- 若要做正式決策支援，可補上資料版本、可重現查詢條件、引用格式與人工覆核流程。

## 八、結語

這個儀表板的核心價值不是把複雜的城市與不動產議題壓縮成單一答案，而是讓資料來源、處理規則、衍生計算與限制條件被看見。當使用者知道一個數字從哪裡來、哪些地方不能推論，才更容易把它用在合適的研究、溝通與決策準備工作上。
